# 项目简报（Project Brief）· 草稿

> 阶段 3 草稿；阶段 4 依据代码与用户确认定稿。**草稿中的“目标/范围”均待用户确认**，现状部分有代码证据。

## 1. 一句话

一个微信小程序：把团队当月的排班截图交给 AI 识别，生成“休 / 正A / 正B / 售A / 售B / IEB / 年假”等彩色日历；成员互看排班，管理员维护成员。

## 2. 为什么做（问题与目标）

- 用户问题：排班表通常是一张 Excel/截图，成员要知道“我今天/本周上什么班”，只能反复翻群里的图片。
- 产品目标：把排班图片变成可点选、可修改、可互看的日历，降低查班成本。
- 初步成功指标（待确认）：导入一次成功率、成员每周打开次数、改班错误率、导入耗时。

## 3. 用户与角色

| 角色 | 能做什么 | 代码位置 |
|---|---|---|
| 未登录用户 | 微信一键登录；绑定已有成员或创建新成员 | `pages/login` |
| 成员（member） | 查看全员排班、改自己的班（**现状后端允许改所有人**，见 BUG-001）、导入排班、个人备忘录 | `pages/calendar`、`pages/import`、`pages/memo` |
| 管理员（admin） | 上述全部 + 切换成员查看、删除成员、成员管理页 | `pages/members`、`calendar.js:225` |
| 系统 | 云函数鉴权、AI 视觉识别、云端存储 | `cloudfunctions/*` |

## 5. 范围（待确认）

- 本期必须：修复权限边界、导入覆盖与月份/年份、成员取消班次、已知视觉缺陷（G4 前确认）。
- 本期可能：Excel 导入、整表导入、新增成员入口、备忘录年份。
- 本期不做（暂定）：多团队/多门店、排班规则校验（工时/连班）、消息推送。

## 6. 约束

- 平台：微信小程序 + 云开发，不能引入自建服务器（当前架构）。
- 数据：线上已有真实排班与成员数据，任何修复不得造成数据丢失。
- 费用：视觉识别按次计费，导入流程应避免重复调用。
- 设计：原设计已上线，默认沿用（待 UI 决策门确认）。
- 时间/人力：单人维护，无自动化测试基线。
