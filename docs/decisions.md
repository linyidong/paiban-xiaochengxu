### D-001 以当前工作区作为线上版本，并建立接手基线

- 日期：2026-10-25
- 背景：仓库只有 1 次提交 `63c2d12 Initial Commit`，工作区有 34 项未提交改动（含删除 `pages/edit`、`components/shift-tag`，新增 `pages/memo`、`cloudfunctions/manageMemo`）。无法从 Git 判断线上对应哪一版。
- 决策：向用户确认「当前工作区 = 线上运行版本」，并以它作为接手基线。
- 理由：用户明确确认；以此为准可保证后续审计、修复与线上一致。未采用“以 Initial Commit 为准”，因为它缺少当前已上线的备忘录、日历内联编辑等功能。
- 影响：
  - 备份到 `D:\Backup\日历排班小程序-backup-20261025`（142 文件 / 202.8 KB / SHA256 全一致）；
  - 基线 commit `6baa8f7`，tag `baseline-before-takeover-20261025`；
  - 后续所有任务 diff 均以此 commit 为对照，可随时回退。

### D-005 go/no-go：建议 go（继续半流程），杀停条件已记录
- 日期：2026-10-25
- 背景：流程 7.7 要求在进入 PRD 前给出继续/停止判断。
- 决策：建议 **go**——技术栈仍在线（小程序 + 云开发）、用户已在实际使用、缺陷可通过最小改动修复，无需重写。
- 理由：现有主链路完整；问题集中在权限、导入语义、选项与视觉，均可在不改数据模型前提下修复。
- 杀停/转向条件（触发则停下向用户报告）：
  1. 用户要求多团队/排班规则引擎/工时结算 → 数据模型需重做，应改走全流程；
  2. 云开发环境无法恢复或视觉 API 停服且无替代；
  3. 线上数据已严重损坏（如大量重复成员/错月排班）且无法安全修复 → 先止损再谈功能。
- 影响：待用户随 UI 决策一并确认；确认前不进入阶段 5 的范围定稿。

### D-006 排班修改权限：成员仅本人，管理员全量

- 日期：2026-10-25
- 背景：现状 `updateShift`/`importShift` 后端零成员级校验，任何登录成员可改任意人排班；前端仅隐藏入口。
- 决策：用户选择 **A——成员只能改自己，管理员可改所有人**。
- 理由：与《初始设计稿.md》第七节的最初设计一致；后端加校验即可，前端调用参数不变，对旧版小程序兼容友好；比“临时授权”改动小。
- 影响：
  - 阶段 7 必须修改 `cloudfunctions/updateShift/index.js` 与 `cloudfunctions/importShift/index.js`，越权返回 `{ok:false,msg}`；
  - 管理员判定复用白名单/`users.role`，需与 `manageMember.checkAdmin` 统一；
  - 需要新增越权回归用例（成员 A 改成员 B 必须失败）；
  - 导入流程中“非管理员选他人”的 UI 路径必须一并收紧（Q-002 确认后实施）。

### D-007 导入权限：成员仅本人，管理员可任意成员/整表

- 日期：2026-10-25
- 背景：现状 `importShift` 的 commit 无权限校验，前端多人识别时允许非管理员选择他人；整表导入（“全部”）在 UI 中不存在。
- 决策：用户选择 **A**——普通成员只能导入自己（上传整表时自动只保留自己那一行）；管理员可导入任意成员，并可“导入整表（全部）”。
- 理由：与 D-006 的权限模型一致；同时把“一次识别、多人入库”做成管理员能力，避免每人重复调用一次视觉 API 的费用。
- 影响：
  - `importShift` 识别阶段可传 `targetName`（成员导入时锁定该成员，省 token），commit 阶段必须校验“目标成员是否本人或管理员”；
  - 前端 `pages/import`：非管理员隐藏成员选择器；管理员增加“全部”选项；
  - `pages/login` 的导入流程同步收紧（避免两套流程行为不一致）；
  - 需要新增越权导入用例（成员导入他人必须失败）。

### D-008 删除成员：软删除并保留历史排班

- 日期：2026-10-25
- 背景：现状 `manageMember.remove` 先删 `shifts` 再删 `users`（`index.js:95-96`），但日历页弹窗写“历史排班将保留”（`calendar.js:242`），两处矛盾。
- 决策：用户选择 **A——软删除，保留历史排班**。
- 理由：与现有文案一致；误删可恢复；审计可追溯；改动集中在查询过滤与一个字段。
- 影响：
  - `users` 增加 `isDeleted:true` + `deletedAt`（默认不写或 `false`）；
  - `remove` 改为更新标记，不再删除 `shifts`/`users`；
  - `getShifts`、`manageMember.list`、`updateShift` 目标查询、`importShift` 建/匹配成员、`login` 多记录合并都必须过滤 `isDeleted`；
  - 同名重建：软删除成员仍占用名字，需允许“恢复”或明确报错（阶段 7 定）；
  - 线上已有成员没有该字段，查询需按“`isDeleted != true`”处理，不能假设字段存在。

### D-009 成员班次编辑：完整班次表 + 取消

### D-010 新设计方向：清爽高对比浅色

- 日期：2026-10-25
- 背景：UI 决策为 B（更换设计），需要先定方向再出规范。

### D-011 日历批量/成员名字改用浅蓝强调（用户指定）

- 日期：2026-10-25
- 背景：用户在实际使用中提出：“批量要移动到与 31 号对齐，批量的背景色与成员名字的背景色都用浅蓝色”。
- 决策：
  1. “批量/完成”按钮缩为一个日期格宽（14.28%），右边缘与 31 号格右边缘对齐；
  2. 批量按钮、成员横滑标签、非管理员“当前成员”区域使用浅蓝底（`#EFF6FF`）；
  3. 选中态用更深浅蓝（`#DBEAFE`）+ 深蓝描边（`#1D4ED8`）区分；
  4. 其他元素位置与全局深青绿主色不变。
- 理由：用户明确要求；浅蓝组合实测对比度 6.70–8.49:1，满足可读性。
- 影响：仅 `app.wxss` 新增 6 个浅蓝 token、`pages/calendar/calendar.wxss` 三处样式；不改 WXML/逻辑；T-013 的深青绿主色继续用于主按钮与导航。
